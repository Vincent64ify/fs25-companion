## Assessment

The application has useful boundaries between game collectors, file transport,
the Python client, relay state, and dashboard rendering. Collector isolation,
command allow-lists, atomic command-file writes, and topic snapshots are good
foundations. The main correctness risk is that the transport treats command
acknowledgements as disposable telemetry. The hosted relay also grants disk
upload access without establishing a trusted client identity.

Seven actionable findings follow. P1 means high priority because of lost
commands/data or exposed server resources; P2 means a significant reliability
or correctness defect. This review does not change application code.

## Findings

### F1 — Rotation discards command acknowledgements and can strand cruise controls

**Location:** [mod/src/Transport.lua:79](../mod/src/Transport.lua#L79),
[mod/src/Scheduler.lua:98](../mod/src/Scheduler.lua#L98),
[client/commands.py:159](../client/commands.py#L159).

`Transport:flush()` writes and flushes its batch, then immediately reopens the
file with `"w"` when the size reaches the rotation threshold. This truncates
the batch before the polling client is guaranteed to read it. The scheduler
resends `hello` and retained state, but it does not retain `command_ack` events.

**Trigger and impact:** A command executes in the frame that crosses the
2 MiB threshold. Its acknowledgement disappears, so the dashboard reports
“no answer” even though the action ran. For `cruise.set`, the client only
releases its coalescing slot after an acknowledgement. A same-session hello
with a higher `commands.next` advances numbering but does not release that
slot. Subsequent cruise changes can remain queued until another suitable
acknowledgement arrives or the game session changes. Repeated user taps can
also repeat a toggle whose first execution appeared to fail.

**Verification:** With a one-byte threshold, sending a real Lua
`command_ack` and calling `flush()` returned a successful rotation but left
an empty file. Separately, a writer with cruise command 1 outstanding still
did not write command 2 after receiving a fresh hello advertising `next=2`.
The existing transport test explicitly expects the truncation, without
checking end-to-end event delivery.

**Recommendation:** Use a reader-aware rotation protocol or retain rotated
segments until consumed. Retain/replay acknowledgements with deduplication;
moving truncation earlier alone does not preserve unread events. Reconcile
the command writer's outstanding state against the mod's progress and provide
bounded recovery for missing acknowledgements.

**Regression check:** Force rotation during a cruise command, verify exactly
one action, delivery of its acknowledgement, and successful delivery of the
next cruise value.

### F2 — File replacement is missed when the stream regrows past its old offset

**Location:** [client/transport/file_tail.py:38](../client/transport/file_tail.py#L38).

`FileTail.poll()` recognizes rotation only when the current size is smaller
than its previous offset. If the mod truncates and refills the file between
polls, the new size can already equal or exceed that offset. The tailer then
returns nothing or seeks into the new stream at the old offset.

**Trigger and impact:** A client starts reading a short stream, is delayed
while the game restarts or rotates, and next observes a replacement at least
as large as the old offset. It skips the new `hello` and potentially static
map topics. The backend can keep old-session state while accepting new
positions until a later correctly detected rotation restores context.

**Verification:** Read `{"old":1}\n`, overwrite the same path with
`{"new":2}\n`, then poll again. The result was `[]`, with no rotation detected.
The existing rotation test covers only a replacement smaller than the offset.

**Recommendation:** Make stream generations explicit and validate them before
resuming an offset. If changing to atomic replacement, track file identity
as well; identity alone cannot detect the current in-place truncation.

**Regression check:** Cover same-size and larger truncate/refill operations,
including a new session hello and an old partial line.

### F3 — Self-declared clients can fill a hosted relay's asset disk

**Location:** [backend/app/ws.py:82](../backend/app/ws.py#L82),
[backend/app/ws.py:94](../backend/app/ws.py#L94),
[backend/app/assets.py:62](../backend/app/assets.py#L62).

Any nonempty pairing string creates a session. Declaring `role="client"`
immediately issues an upload token; there is no trusted enrollment step.
That token authorizes uploads to any valid map/hash path. Individual file
size limits do not limit the number of uploads or aggregate disk use.

**Trigger and impact:** An anonymous visitor to a hosted relay chooses a new
pairing string, receives a token, and uploads files under arbitrarily many
different digests. This can exhaust persistent storage without knowing an
existing user's pairing code. It contradicts the asset module's stated
protection against random visitors filling the disk. Uploaded files remain
after the connection and in-memory session disappear.

**Verification:** A connection using a previously unused pairing string and
only `{"type":"hello","role":"client"}` received a token. A subsequent PUT
of arbitrary bytes to `overview.png` returned HTTP 201 and persisted the file.
No external service was contacted or filled during this check.

**Recommendation:** Require a server-issued enrollment credential or other
explicit upload authorization for hosted clients. Add per-principal and global
storage quotas, upload rate limits, and expiration/cleanup. Bind upload
permissions to the authorized asset scope. Preserve the intended LAN workflow
through an explicit local-mode policy.

**Regression check:** An unregistered connection must not gain persistent
upload access merely by claiming a role; authorized uploads must respect
aggregate quotas.

### F4 — One slow viewer can stall telemetry for its entire session

**Location:** [backend/app/sessions.py:17](../backend/app/sessions.py#L17),
[backend/app/sessions.py:41](../backend/app/sessions.py#L41),
[backend/app/ws.py:145](../backend/app/ws.py#L145).

Broadcasting awaits every viewer's `send_text()` sequentially, without a
deadline or independent output queue. `handle_client()` awaits that broadcast
before receiving the next game message. Catching send exceptions does not
help while a send is waiting on network backpressure.

**Trigger and impact:** A tablet stops consuming data while its connection
remains open. Once its network buffers fill, the game-message receiver stalls,
delaying updates and acknowledgements for healthy viewers too. The Python
client's latest-value outbox does not resolve this backend blockage.

**Verification:** A viewer double whose `send_text()` never completes kept
`Session.broadcast()` pending until an external timeout cancelled it. This
confirms the scheduling dependency; real network buffer thresholds were not
measured.

**Recommendation:** Give each viewer a bounded output queue and independent
sender, coalesce telemetry, and disconnect stalled consumers after a deadline.
Keep command acknowledgements distinguishable from replaceable state.

**Regression check:** A blocked viewer must not prevent another viewer from
receiving updates or the backend from processing the next envelope.

### F5 — JSON escaping depends on locale and corrupts UTF-8

**Location:** [mod/src/Json.lua:23](../mod/src/Json.lua#L23).

The encoder uses Lua's locale-sensitive `%c` character class to find control
bytes. On the reviewed macOS runtime, this includes byte `0x96`, which can
occur inside a valid UTF-8 sequence. Escaping that byte independently leaves
the preceding UTF-8 lead byte without its continuation byte.

**Trigger and impact:** Encoding `PÖTTINGER` produced bytes equivalent to
`"P\xc3\\u0096TTINGER"`, which are not valid UTF-8. The fixture check fails
with `UnicodeDecodeError`; the production tailer's replacement decoding would
instead corrupt affected names. The behavior in the game's embedded runtime
still needs a live check, but the repository's supported macOS test path
already fails.

**Verification:** `test_rig_fixtures_are_up_to_date` fails in the plow fixture.
Directly calling the same encoder with `PÖTTINGER` reproduces the invalid bytes.

**Recommendation:** Match JSON's explicit ASCII control range `0x00–0x1F`,
quotation mark, and backslash, preserving UTF-8 bytes above that range.

**Regression check:** Round-trip accented names, non-Latin names, emoji, and
every required JSON control escape under the supported runtimes/locales.

### F6 — Malformed command actions escape validation and terminate the viewer

**Location:** [backend/app/ws.py:185](../backend/app/ws.py#L185).

`action not in COMMAND_ACTIONS` runs before checking that `action` is a string.
Lists and objects decoded from valid JSON are unhashable, so this membership
check raises `TypeError`. The viewer loop catches only `WebSocketDisconnect`.

**Trigger and impact:** Sending
`{"type":"command","id":"1","action":[]}` terminates that viewer handler
instead of returning the normal rejection acknowledgement. This is scoped to
the offending viewer; it does not establish a server-wide crash.

**Verification:** Calling `handle_command()` with that payload raised
`TypeError("unhashable type: 'list'")`.

**Recommendation:** Validate the command shape before allow-list lookup,
including an explicit string check for `action`.

**Regression check:** Arrays, objects, null, booleans, and numeric actions
should be rejected while allowing a subsequent valid command on the socket.

### F7 — The dashboard never clears a recovered protocol mismatch

**Location:** [backend/app/ws.py:141](../backend/app/ws.py#L141),
[web/src/connection.js:102](../web/src/connection.js#L102).

After a valid envelope, the backend clears `session.protocol_error` locally
but sends no clear message. The browser only updates its `protocolError`
store key when receiving a `protocol_error` message. Topic snapshots and
reconnections do not reset that key.

**Trigger and impact:** A viewer sees a version mismatch, then the user fixes
the mod/client and reconnects successfully. The original browser continues
showing the update-required banner while telemetry is working. Reloading the
page clears it, but reconnecting alone does not.

**Recommendation:** Explicitly broadcast protocol recovery when the error
state changes, and include current protocol status in connection initialization.

**Regression check:** Send an incompatible envelope followed by a compatible
one and confirm that the already-open viewer's banner disappears, including
after reconnecting to a healthy backend.

## Suggested order of work

1. Preserve acknowledgements across rotation and recover outstanding commands
   (F1), then make stream generation detection reliable (F2).
2. Establish hosted upload authorization and storage limits (F3) before
   exposing a relay publicly.
3. Isolate slow viewers (F4) and fix the reproduced UTF-8 test failure (F5).
4. Harden command parsing and protocol recovery (F6–F7), then complete the
   WebSocket, browser, and live-game validation.
